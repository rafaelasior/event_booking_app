# REQUIREMENTS.md

# Εφαρμογή Διαχείρισης Εκδηλώσεων και Ηλεκτρονικών Κρατήσεων

Το αρχείο αυτό μετατρέπει την εκφώνηση της υποχρεωτικής εργασίας σε checklist, ώστε να χρησιμοποιείται για σχεδιασμό, υλοποίηση, έλεγχο προόδου και τελικό verification.

## Κατάσταση

- `[ ]` Δεν έχει ξεκινήσει
- `[-]` Σε εξέλιξη
- `[x]` Ολοκληρώθηκε και ελέγχθηκε

---

# 1. Γενικός στόχος και αρχιτεκτονική

- [ ] Να αναπτυχθεί εφαρμογή διαχείρισης εκδηλώσεων και ηλεκτρονικών κρατήσεων εισιτηρίων/θέσεων στον Παγκόσμιο Ιστό.
- [ ] Η εφαρμογή να βασίζεται σε αρχιτεκτονική web browser / web server.
- [ ] Όλες οι λειτουργίες της εφαρμογής να είναι προσβάσιμες μέσω web browser.
- [ ] Να υπάρχει σαφής διαχωρισμός frontend, backend και βάσης δεδομένων.
- [ ] Να σχεδιαστεί σχεσιακή βάση δεδομένων για χρήστες, εκδηλώσεις, τύπους εισιτηρίων, κρατήσεις, μηνύματα και τις υπόλοιπες απαιτούμενες πληροφορίες.
- [ ] Όλες οι αλληλεπιδράσεις client–server να είναι κρυπτογραφημένες μέσω SSL/TLS.

---

# 2. Ρόλοι χρηστών

Η εφαρμογή πρέπει να υποστηρίζει τέσσερις ρόλους:

- [ ] Διαχειριστής Εφαρμογής
- [ ] Διοργανωτής
- [ ] Συμμετέχων
- [ ] Επισκέπτης

## 2.1 Διαχειριστής

- [ ] Να υπάρχει ενσωματωμένος διαχειριστής από την εγκατάσταση της εφαρμογής.
- [ ] Ο διαχειριστής να μπορεί να συνδεθεί με username και password.
- [ ] Μετά την επιτυχή σύνδεση να οδηγείται στη σελίδα διαχείρισης χρηστών.
- [ ] Να μπορεί να βλέπει τη λίστα χρηστών.
- [ ] Να μπορεί να ανοίγει τη σελίδα στοιχείων κάθε χρήστη.
- [ ] Να μπορεί να εξετάζει όλα τα στοιχεία του χρήστη.
- [ ] Να μπορεί να εγκρίνει νέες αιτήσεις εγγραφής.
- [ ] Να μπορεί να απορρίπτει νέες αιτήσεις εγγραφής.
- [ ] Να μπορεί να εξάγει τις εκδηλώσεις σε XML.
- [ ] Η εξαγωγή XML να ακολουθεί το DTD της εκφώνησης.
- [ ] Να μπορεί να εξάγει τις εκδηλώσεις σε αντίστοιχη μορφή JSON.

## 2.2 Διοργανωτής

- [ ] Κάθε εγγεγραμμένος χρήστης να μπορεί να λειτουργήσει ως διοργανωτής.
- [ ] Να μπορεί να δημιουργεί μία ή περισσότερες εκδηλώσεις.
- [ ] Να μπορεί να αποθηκεύει εκδήλωση ως draft.
- [ ] Να μπορεί να δημοσιεύει εκδήλωση.
- [ ] Να μπορεί να βλέπει τις ενεργές εκδηλώσεις που έχει δημιουργήσει.
- [ ] Να μπορεί να βλέπει τις κρατήσεις κάθε δικής του εκδήλωσης.
- [ ] Να μπορεί να τροποποιεί τα στοιχεία μιας εκδήλωσης.
- [ ] Να μπορεί να ακυρώνει δημοσιευμένη εκδήλωση.
- [ ] Να μπορεί να διαγράφει εκδήλωση μόνο όταν επιτρέπεται από τους κανόνες της εκφώνησης.
- [ ] Να μπορεί να επικοινωνεί με συμμετέχοντες που έχουν κάνει κράτηση.
- [ ] Σε ακύρωση εκδήλωσης, να μπορεί να αποστέλλει ενημερωτικό μήνυμα σε όλους τους χρήστες που έχουν κράτηση.

## 2.3 Συμμετέχων

- [ ] Κάθε εγγεγραμμένος χρήστης να μπορεί να λειτουργήσει ως συμμετέχων.
- [ ] Να μπορεί να πλοηγείται στις εκδηλώσεις άλλων χρηστών.
- [ ] Να μπορεί να αναζητά εκδηλώσεις.
- [ ] Να μπορεί να βλέπει αναλυτικά στοιχεία εκδήλωσης.
- [ ] Να μπορεί να πραγματοποιεί κράτηση όταν πληρούνται οι προϋποθέσεις.
- [ ] Να μπορεί να πραγματοποιεί περισσότερες από μία κρατήσεις στην ίδια εκδήλωση, εφόσον υπάρχουν διαθέσιμες θέσεις.
- [ ] Να μπορεί να επικοινωνεί με τον διοργανωτή μετά την πραγματοποίηση κράτησης.

## 2.4 Επισκέπτης

- [ ] Ο επισκέπτης να μπορεί να βλέπει τη σελίδα καλωσορίσματος.
- [ ] Ο επισκέπτης να μπορεί να πλοηγείται στις εκδηλώσεις.
- [ ] Ο επισκέπτης να μπορεί να αναζητά εκδηλώσεις.
- [ ] Ο επισκέπτης να μην μπορεί να πραγματοποιεί κρατήσεις.

---

# 3. Σελίδα καλωσορίσματος και authentication

- [ ] Η εφαρμογή να εμφανίζει αρχικά welcome page.
- [ ] Η welcome page να περιλαμβάνει κουμπί εγγραφής.
- [ ] Η welcome page να περιλαμβάνει δυνατότητα εισόδου.
- [ ] Η φόρμα εισόδου να ζητά username.
- [ ] Η φόρμα εισόδου να ζητά password.
- [ ] Να γίνεται έλεγχος εγκυρότητας των credentials.
- [ ] Να υλοποιηθεί ασφαλής μηχανισμός authentication.
- [ ] Να υλοποιηθεί authorization ανά ρόλο.
- [ ] Τα προστατευμένα endpoints να μην είναι διαθέσιμα χωρίς έγκυρη πιστοποίηση.
- [ ] Τα passwords να μην αποθηκεύονται ως απλό κείμενο.
- [ ] Η εφαρμογή να χειρίζεται αποτυχημένο login με σαφές μήνυμα.
- [ ] Η εφαρμογή να χειρίζεται χρήστη του οποίου η αίτηση δεν έχει ακόμη εγκριθεί.
- [ ] Η εφαρμογή να χειρίζεται χρήστη του οποίου η αίτηση έχει απορριφθεί.

---

# 4. Εγγραφή νέου χρήστη

Η σελίδα εγγραφής πρέπει να ζητά τουλάχιστον:

- [ ] Username
- [ ] Password
- [ ] Επιβεβαίωση password
- [ ] Όνομα
- [ ] Επώνυμο
- [ ] Email
- [ ] Τηλέφωνο επικοινωνίας
- [ ] Στοιχεία διεύθυνσης
- [ ] Γεωγραφική τοποθεσία
- [ ] ΑΦΜ
- [ ] Οποιαδήποτε επιπλέον στοιχεία είναι απαραίτητα για την εφαρμογή

## Έλεγχοι εγγραφής

- [ ] Το username να είναι μοναδικό.
- [ ] Αν το username χρησιμοποιείται, να ζητείται νέο username.
- [ ] Το password και η επιβεβαίωση password να συμφωνούν.
- [ ] Να γίνεται validation των απαιτούμενων πεδίων.
- [ ] Να γίνεται validation email.
- [ ] Να γίνεται validation των υπόλοιπων πεδίων όπου απαιτείται.
- [ ] Μετά την επιτυχή υποβολή να δημιουργείται αίτηση εγγραφής σε εκκρεμότητα.
- [ ] Ο νέος χρήστης να ενημερώνεται ότι εκκρεμεί έγκριση από τον διαχειριστή.
- [ ] Ο χρήστης να μην αποκτά πλήρη πρόσβαση πριν εγκριθεί.

---

# 5. Αρχική σελίδα εγγεγραμμένου χρήστη

- [ ] Μετά από επιτυχή είσοδο, ο εγγεγραμμένος χρήστης να οδηγείται στην αρχική σελίδα.
- [ ] Η αρχική σελίδα να παρέχει πρόσβαση στη διαχείριση εκδηλώσεων.
- [ ] Η αρχική σελίδα να παρέχει πρόσβαση στην πλοήγηση/αναζήτηση εκδηλώσεων.
- [ ] Η αρχική σελίδα να εμφανίζει κατάλληλη ένδειξη για νέα μηνύματα.
- [ ] Η αρχική σελίδα να εμφανίζει προτεινόμενες εκδηλώσεις σε κατάλληλο τμήμα της διεπαφής.

---

# 6. Μοντέλο εκδήλωσης

Κάθε εκδήλωση πρέπει να περιλαμβάνει:

- [ ] `EventID`: μοναδικό αναγνωριστικό εκδήλωσης.
- [ ] `Title`: σύντομος τίτλος.
- [ ] `Category`: μία ή περισσότερες κατηγορίες.
- [ ] `EventType`: τύπος εκδήλωσης.
- [ ] `Venue`: χώρος διεξαγωγής.
- [ ] `Address`: διεύθυνση.
- [ ] `City`: πόλη.
- [ ] `Country`: χώρα.
- [ ] `GeoLocation`: προαιρετική γεωγραφική τοποθεσία.
- [ ] `Latitude`: γεωγραφικό πλάτος όταν υπάρχει GeoLocation.
- [ ] `Longitude`: γεωγραφικό μήκος όταν υπάρχει GeoLocation.
- [ ] `StartDateTime`: ημερομηνία και ώρα έναρξης.
- [ ] `EndDateTime`: ημερομηνία και ώρα λήξης.
- [ ] `Capacity`: συνολική χωρητικότητα.
- [ ] `TicketTypes`: ένας ή περισσότεροι τύποι εισιτηρίων.
- [ ] `Bookings`: μηδέν ή περισσότερες κρατήσεις.
- [ ] `Organizer`: αναφορά στον διοργανωτή.
- [ ] `Status`: κατάσταση εκδήλωσης.
- [ ] `Description`: πλήρης περιγραφή.
- [ ] `Media`: προαιρετικό οπτικό υλικό.
- [ ] `Photo`: μηδέν ή περισσότερες φωτογραφίες.

## 6.1 Κατηγορίες

- [ ] Μία εκδήλωση να μπορεί να ανήκει σε περισσότερες από μία κατηγορίες.
- [ ] Οι κατηγορίες να αποθηκεύονται σωστά στη σχεσιακή βάση.
- [ ] Οι κατηγορίες να μπορούν να χρησιμοποιηθούν για πλοήγηση και αναζήτηση.

## 6.2 Τύποι εισιτηρίων

Κάθε τύπος εισιτηρίου πρέπει να περιλαμβάνει:

- [ ] `TicketTypeID`: μοναδικό αναγνωριστικό τύπου εισιτηρίου.
- [ ] `Name`: όνομα τύπου εισιτηρίου.
- [ ] `Price`: τιμή.
- [ ] `Quantity`: συνολικό πλήθος εισιτηρίων αυτού του τύπου.
- [ ] `Available`: διαθέσιμο υπόλοιπο.

## 6.3 Καταστάσεις εκδήλωσης

Να υποστηρίζονται τουλάχιστον:

- [ ] `DRAFT`
- [ ] `PUBLISHED`
- [ ] `COMPLETED`
- [ ] `CANCELLED`

---

# 7. Δημιουργία και δημοσίευση εκδήλωσης

- [ ] Να υπάρχει κατάλληλη διεπαφή δημιουργίας νέας εκδήλωσης.
- [ ] Ο διοργανωτής να μπορεί να συμπληρώνει όλα τα απαιτούμενα στοιχεία.
- [ ] Να μπορεί να ορίζει μία ή περισσότερες κατηγορίες.
- [ ] Να μπορεί να ορίζει έναν ή περισσότερους τύπους εισιτηρίων.
- [ ] Να μπορεί να ορίζει συνολική χωρητικότητα.
- [ ] Να μπορεί να ανεβάζει προαιρετικά μία ή περισσότερες φωτογραφίες.
- [ ] Να γίνεται validation ημερομηνίας έναρξης και λήξης.
- [ ] Η ημερομηνία λήξης να μην προηγείται της ημερομηνίας έναρξης.
- [ ] Η χωρητικότητα να είναι θετικός αριθμός.
- [ ] Οι ποσότητες εισιτηρίων να είναι έγκυρες μη αρνητικές τιμές.
- [ ] Οι τιμές εισιτηρίων να είναι έγκυρες μη αρνητικές τιμές.
- [ ] Το άθροισμα των ποσοτήτων όλων των τύπων εισιτηρίων να μην υπερβαίνει τη συνολική χωρητικότητα.
- [ ] Η εκδήλωση να μπορεί να αποθηκευτεί πριν δημοσιευτεί.
- [ ] Ο διοργανωτής να μπορεί να επιλέξει τη δημοσίευσή της.
- [ ] Μετά τη δημοσίευση να εφαρμόζονται οι σχετικοί περιορισμοί τροποποίησης/διαγραφής.

---

# 8. Διαχείριση εκδηλώσεων από τον διοργανωτή

- [ ] Να εμφανίζεται λίστα ενεργών εκδηλώσεων του διοργανωτή.
- [ ] Να εμφανίζονται τα αναλυτικά στοιχεία κάθε εκδήλωσης.
- [ ] Να εμφανίζονται οι κρατήσεις κάθε εκδήλωσης.
- [ ] Ο διοργανωτής να μπορεί να επεξεργάζεται τα στοιχεία εκδήλωσης.
- [ ] Να ελέγχονται ξανά οι κανόνες χωρητικότητας κατά την τροποποίηση.
- [ ] Να μην επιτρέπεται τροποποίηση τύπων εισιτηρίων που οδηγεί σε συνολικό πλήθος μεγαλύτερο από τη χωρητικότητα.
- [ ] Να προστατεύεται η συνέπεια με τις ήδη υπάρχουσες κρατήσεις.

## 8.1 Διαγραφή εκδήλωσης

- [ ] Η διαγραφή να επιτρέπεται πριν από τη δημοσίευση.
- [ ] Η διαγραφή να επιτρέπεται το αργότερο πριν από την πρώτη κράτηση.
- [ ] Να μην επιτρέπεται διαγραφή όταν υπάρχει ήδη κράτηση.
- [ ] Να μην επιτρέπεται διαγραφή δημοσιευμένης εκδήλωσης όταν παραβιάζεται ο παραπάνω κανόνας.
- [ ] Η εφαρμογή να εμφανίζει σαφές μήνυμα όταν η διαγραφή δεν επιτρέπεται.

## 8.2 Ακύρωση εκδήλωσης

- [ ] Η ακύρωση να αφορά ήδη δημοσιευμένη εκδήλωση.
- [ ] Με την ακύρωση, το status να γίνεται `CANCELLED`.
- [ ] Η ακύρωση να μην διαγράφει τα δεδομένα της εκδήλωσης.
- [ ] Μετά την ακύρωση να μην επιτρέπονται νέες κρατήσεις.
- [ ] Οι υπάρχουσες κρατήσεις να παραμένουν αποθηκευμένες.
- [ ] Οι υπάρχουσες κρατήσεις να μπορούν να επισημαίνονται ως ακυρωμένες ή μη ενεργές, ανάλογα με τον σχεδιασμό.
- [ ] Να διατηρείται ιστορικότητα και ιχνηλασιμότητα.
- [ ] Να υποστηρίζεται ενημερωτικό μήνυμα προς όλους τους χρήστες που έχουν κράτηση.

---

# 9. Διαχείριση χωρητικότητας και διαθεσιμότητας

Για κάθε εκδήλωση πρέπει να τηρούνται:

- [ ] Συνολική χωρητικότητα.
- [ ] Διαθέσιμες θέσεις ανά τύπο εισιτηρίου.
- [ ] Συνολικό πλήθος δεσμευμένων θέσεων.

## Κανόνες

- [ ] Το άθροισμα των ποσοτήτων των τύπων εισιτηρίων να μην υπερβαίνει τη συνολική χωρητικότητα.
- [ ] Να μην επιτρέπεται δημιουργία τύπου εισιτηρίου που παραβιάζει τη χωρητικότητα.
- [ ] Να μην επιτρέπεται τροποποίηση τύπου εισιτηρίου που παραβιάζει τη χωρητικότητα.
- [ ] Να μην επιτρέπεται κράτηση χωρίς επαρκείς διαθέσιμες θέσεις.
- [ ] Να μην επιτρέπεται κράτηση που παραβιάζει τη συνολική χωρητικότητα.
- [ ] Μετά από επιτυχή κράτηση να μειώνεται σωστά το `Available`.
- [ ] Μετά από επιτυχή κράτηση να αυξάνεται σωστά το συνολικό πλήθος δεσμευμένων θέσεων.
- [ ] Οι έλεγχοι διαθεσιμότητας και η ενημέρωση να γίνονται με τρόπο που αποφεύγει ασυνέπειες από ταυτόχρονες κρατήσεις.

# 10. Πλοήγηση και αναζήτηση εκδηλώσεων

- [ ] Να υπάρχει σελίδα πλοήγησης/αναζήτησης εκδηλώσεων.
- [ ] Να υποστηρίζεται πλοήγηση βάσει κατηγορίας.
- [ ] Να υποστηρίζεται αναζήτηση βάσει κατηγορίας.
- [ ] Να υποστηρίζεται αναζήτηση βάσει τίτλου.
- [ ] Να υποστηρίζεται αναζήτηση βάσει περιγραφής.
- [ ] Η αναζήτηση τίτλου/περιγραφής να υποστηρίζει ελεύθερο κείμενο.
- [ ] Να υποστηρίζεται αναζήτηση βάσει χρονικού διαστήματος.
- [ ] Να υποστηρίζεται αναζήτηση βάσει τιμής εισιτηρίου.
- [ ] Να υποστηρίζεται αναζήτηση βάσει τοποθεσίας.
- [ ] Να μπορεί να χρησιμοποιείται συνδυασμός φίλτρων, εφόσον επιλεγεί στον σχεδιασμό.
- [ ] Τα αποτελέσματα να εμφανίζονται σε πίνακες.
- [ ] Οι πίνακες να είναι κατάλληλα σελιδοποιημένοι.
- [ ] Η πλοήγηση ανάμεσα στις σελίδες αποτελεσμάτων να είναι εύχρηστη.
- [ ] Οι επισκέπτες να μπορούν να χρησιμοποιούν την πλοήγηση και την αναζήτηση.
- [ ] Να εμφανίζονται μόνο εκδηλώσεις που επιτρέπεται να είναι ορατές στο κοινό.

# 11. Αναλυτική σελίδα εκδήλωσης

- [ ] Να εμφανίζονται όλα τα αναλυτικά στοιχεία της εκδήλωσης.
- [ ] Να εμφανίζονται οι διαθέσιμοι τύποι εισιτηρίων.
- [ ] Να εμφανίζονται οι τιμές.
- [ ] Να εμφανίζονται οι διαθέσιμες ποσότητες.
- [ ] Να εμφανίζονται οι φωτογραφίες, όταν υπάρχουν.
- [ ] Να εμφανίζεται χάρτης OpenStreetMap.
- [ ] Στον χάρτη να εμφανίζεται η γεωγραφική τοποθεσία της εκδήλωσης.
- [ ] Για εγγεγραμμένο και εγκεκριμένο χρήστη να εμφανίζεται δυνατότητα κράτησης.
- [ ] Για επισκέπτη να μην επιτρέπεται κράτηση.
- [ ] Για ακυρωμένη ή μη ενεργή εκδήλωση να μην επιτρέπεται κράτηση.

# 12. Κρατήσεις

Κάθε κράτηση πρέπει να περιλαμβάνει:

- [ ] `BookingID`: μοναδικό αναγνωριστικό κράτησης.
- [ ] `Attendee`: αναφορά στον χρήστη.
- [ ] `Time`: χρόνος πραγματοποίησης κράτησης.
- [ ] `TicketTypeRef`: αναφορά στον τύπο εισιτηρίου.
- [ ] `NumberOfTickets`: αριθμός εισιτηρίων.
- [ ] `TotalCost`: συνολικό κόστος.
- [ ] `BookingStatus`: κατάσταση κράτησης.

## 12.1 Καταστάσεις κράτησης

Να υποστηρίζονται τουλάχιστον:

- [ ] `PENDING`
- [ ] `CONFIRMED`
- [ ] `CANCELLED`

## 12.2 Ροή κράτησης

- [ ] Η κράτηση να επιτρέπεται μόνο όταν η εκδήλωση είναι ενεργή.
- [ ] Η κράτηση να επιτρέπεται μόνο όταν υπάρχουν διαθέσιμες θέσεις.
- [ ] Ο χρήστης να επιλέγει τύπο εισιτηρίου.
- [ ] Ο χρήστης να επιλέγει αριθμό εισιτηρίων.
- [ ] Να υπολογίζεται σωστά το συνολικό κόστος.
- [ ] Πριν την οριστική υποβολή να ζητείται επιβεβαίωση.
- [ ] Να ενημερώνεται ο χρήστης ότι η κράτηση δεν μπορεί να αναιρεθεί μετά την οριστική υποβολή.
- [ ] Να μην παρέχεται δυνατότητα αναίρεσης της οριστικά υποβληθείσας κράτησης.
- [ ] Να επιτρέπονται μία ή περισσότερες κρατήσεις από τον ίδιο χρήστη στην ίδια εκδήλωση, εφόσον υπάρχουν θέσεις.

## 12.3 Έλεγχοι κράτησης

Κατά την υποβολή να ελέγχεται ότι:

- [ ] Ο ζητούμενος αριθμός εισιτηρίων είναι θετικός.
- [ ] Ο ζητούμενος τύπος εισιτηρίου υπάρχει.
- [ ] Ο ζητούμενος αριθμός εισιτηρίων είναι διαθέσιμος για τον συγκεκριμένο τύπο.
- [ ] Δεν παραβιάζεται η συνολική χωρητικότητα.
- [ ] Η εκδήλωση δεν είναι ακυρωμένη.
